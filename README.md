# Lens API

Бэкенд-сервис для лендинг-презентации разработчика: форма обратной связи с валидацией,
AI-анализом входящих обращений, отправкой писем, файловым логированием и защитой от спама.

| | |
|---|---|
| **Живой API** | https://lens-api.farhat.one |
| **Swagger** | https://lens-api.farhat.one/docs |
| **ReDoc** | https://lens-api.farhat.one/redoc |
| **Состояние сервиса** | https://lens-api.farhat.one/api/health |
| **Статистика** | https://lens-api.farhat.one/api/metrics |

### Попробовать за десять секунд

```bash
curl -X POST https://lens-api.farhat.one/api/contact \
  -H 'Content-Type: application/json' \
  -d '{
    "name": "Иван Петров",
    "phone": "+7 999 123-45-67",
    "email": "ivan@example.com",
    "comment": "Здравствуйте! Хотел бы обсудить backend-проект для нашей команды."
  }'
```

В ответе придут `sentiment` и `category`, определённые моделью, а на указанный email —
подтверждение. Ограничение: 5 обращений в час с одного IP.

Больше примеров, включая ошибки валидации и срабатывание лимита, —
в [`examples/`](examples/) (curl-скрипт и коллекция Postman).

## 1. Как запустить проект

### Вариант A — Docker (рекомендуется)

Единственное требование — Docker с плагином Compose.

```bash
git clone <repo-url>
cd backend

cp .env.example .env      # заполнить ключи, см. таблицу ниже
docker compose up -d

curl http://localhost:8000/api/health
```

Миграции применяются автоматически при старте контейнера — отдельных шагов не требуется.
Swagger доступен на http://localhost:8000/docs.

Остановить: `docker compose down` (данные сохраняются в volume `api-data`).

### Вариант B — локально, без Docker

Требуется Python 3.10+ (проект разрабатывался на 3.12).

```bash
cd backend

python3 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env               # заполнить ключи

alembic upgrade head               # создать схему БД
uvicorn app.main:app --reload
```

> Приложение намеренно **не создаёт таблицы само**. Если забыть про миграции,
> оно упадёт на старте с понятным сообщением, а не с `no such table` на первом
> запросе. Схемой владеет Alembic — единственный источник правды.

### Переменные окружения

| Переменная | Обязательна | По умолчанию | Назначение |
|---|---|---|---|
| `ENVIRONMENT` | нет | `development` | `development` / `production` |
| `DEBUG` | нет | `true` | Подробные ошибки в ответах API |
| `CORS_ORIGINS` | нет | localhost:3000,5173 | Разрешённые источники, через запятую |
| `DATABASE_URL` | нет | `sqlite+aiosqlite:///./data/app.db` | Строка подключения к БД |
| `DATA_DIR` | нет | `./data` | Каталог логов, БД и состояния rate-limit |
| `RATE_LIMIT_MAX_REQUESTS` | нет | `5` | Запросов на IP за окно |
| `RATE_LIMIT_WINDOW_SECONDS` | нет | `3600` | Длина окна в секундах |
| `AI_PROVIDER_CHAIN` | нет | `gemini,openai` | Порядок провайдеров; первый — основной |
| `AI_TIMEOUT_SECONDS` | нет | `8` | Таймаут на одного провайдера |
| `GEMINI_API_KEY` | для AI | — | Ключ Google AI Studio |
| `OPENAI_API_KEY` | для AI | — | Ключ OpenAI |
| `SMTP_HOST` / `SMTP_PORT` | для почты | — | SMTP-сервер |
| `SMTP_USER` / `SMTP_PASSWORD` | для почты | — | Учётные данные SMTP |
| `MAIL_FROM` | для почты | — | Адрес отправителя |
| `OWNER_EMAIL` | для почты | — | Куда приходят уведомления |

**Сервис запускается и работает без единого ключа.** Без AI-ключей обращения
сохраняются с нейтральным анализом, без SMTP — письма пропускаются. `/api/health`
честно показывает, что именно не настроено.

> ⚠️ Переменные окружения имеют **приоритет над `.env`**. Если в вашей оболочке
> экспортирован, например, `OPENAI_API_KEY`, он перекроет пустое значение из файла.
> Это стандартное 12-factor поведение, но при отладке об этом легко забыть.

### Тесты

```bash
pip install -r requirements-dev.txt
pytest
```

35 тестов, выполняются за ~1.5 секунды. Сеть не используется: AI-провайдеры
подменяются заглушками, поэтому тесты детерминированы и не тратят квоту.

### Слои

```
HTTP → Controller → Service → Repository → хранилище
       (routes)     (логика)   (доступ)     (БД / файлы)
```

Правило одно: слой знает только о слое под собой. Роут не обращается к БД,
репозиторий ничего не знает об HTTP. Практическая польза — тесты AI-цепочки
работают без поднятия приложения, а замена SQLite на Postgres не касается
бизнес-логики.

### Применённые паттерны

**Repository** — доступ к данным изолирован. `SubmissionRepository` работает с БД,
`RateLimiter` — с памятью и файлом. Сервисам всё равно, что под ними.

**Strategy** — `AIAnalyzer` описывает контракт «текст → анализ». Gemini и OpenAI
реализуют его независимо, `AIService` перебирает их по порядку. Добавить третьего
провайдера — новый класс и строка в реестре.

**Dependency Injection** — долгоживущие объекты (AI-цепочка, почта, rate-limiter)
создаются один раз при старте и живут в `app.state`. FastAPI раздаёт их в роуты
через `Depends`. Пересоздание на каждый запрос заново читало бы конфиг и
поднимало HTTP-клиенты.

**Middleware** — логирование запросов вынесено из обработчиков: ни один роут
не знает, что его пишут в файл.

## 4. Реализация API

Все эндпоинты под префиксом `/api`. Полная интерактивная документация — `/docs`.

### `POST /api/contact`

Запрос:

```json
{
  "name": "Иван Петров",
  "phone": "+7 999 123-45-67",
  "email": "ivan@example.com",
  "comment": "Здравствуйте! Хотел бы обсудить backend-проект."
}
```

Ответ `201 Created`:

```json
{
  "success": true,
  "message": "Your message has been received. We will get back to you shortly.",
  "data": {
    "submission_id": "7d6241a5-4df2-4669-ab63-ece89c611e8a",
    "created_at": "2026-07-22T10:29:44.688661Z",
    "sentiment": "positive",
    "category": "collaboration",
    "ai_status": "ok",
    "email_sent": true
  }
}
```

### Валидация

| Поле | Правила |
|---|---|
| `name` | 2–100 символов, должно содержать буквы |
| `phone` | 7–15 цифр, допустимы `+`, пробелы, `-`, `( )` |
| `email` | Проверка формата через `email-validator` |
| `comment` | 10–5000 символов |

Дополнительно из всех текстовых полей вырезаются управляющие и невидимые символы —
это защита от инъекции заголовков в письмо и от обхода проверок длины невидимой
набивкой. Пользовательский текст попадает в HTML-письма через Jinja2 с включённым
автоэкранированием.

### Обработка ошибок

Любая ошибка возвращается в одном формате — клиенту не нужно разбираться, какой
слой сломался:

```json
{
  "error": {
    "code": "validation_error",
    "message": "Invalid input data.",
    "details": [
      { "field": "email", "message": "value is not a valid email address", "type": "value_error" }
    ]
  },
  "request_id": "cb08fadf-febf-4d65-abec-010dd757654b"
}
```

`request_id` дублируется в заголовке `X-Request-ID` и в файле логов — по нему
можно найти конкретный запрос при разборе инцидента.

| Код | Когда |
|---|---|
| `201` | Обращение принято |
| `422` | Ошибка валидации, с разбивкой по полям |
| `429` | Превышен лимит; в заголовке `Retry-After` — через сколько секунд можно повторить |
| `404` / `405` | Неизвестный маршрут или метод |
| `503` | Не удалось сохранить обращение |
| `500` | Непредвиденная ошибка; при `DEBUG=false` детали наружу не отдаются |

### `GET /api/health`

Проверяет БД и сообщает состояние AI и SMTP. Используется как healthcheck
контейнера, поэтому намеренно дешёвый: не ходит в AI-провайдеры и на SMTP-сервер.
Healthcheck, который каждые 30 секунд делает платные вызовы, — сам по себе авария.

Статусы: `ok` — всё настроено; `degraded` — БД жива, но AI или почта не настроены;
`unhealthy` — недоступна БД.

### `GET /api/metrics`

```json
{
  "total_submissions": 42,
  "submissions_last_24h": 7,
  "by_sentiment": { "positive": 30, "neutral": 9, "negative": 3 },
  "by_category": { "job": 12, "collaboration": 18, "support": 8, "spam": 4 },
  "ai_success_rate": 0.9762,
  "by_ai_provider": { "gemini": 39, "openai": 2 },
  "generated_at": "2026-07-22T10:29:44.560355Z"
}
```

Примеры запросов — в [`examples/`](examples/) (curl + коллекция Postman).

## 5. AI-интеграция

### Что делает

Один вызов модели решает три задачи сразу — они опираются на один и тот же контекст,
поэтому три отдельных запроса утроили бы задержку и стоимость без выигрыша в качестве:

1. **Тональность** — `positive` / `neutral` / `negative`
2. **Классификация** — `job` / `collaboration` / `support` / `spam` / `other`
3. **Черновик ответа** — 2–4 предложения на языке обращения

Результат сохраняется в БД, попадает в письмо владельцу и агрегируется в `/api/metrics`.

### Промпт

Системный:

```
You analyse messages submitted through a software developer's contact form.
For each message determine the sender's sentiment, classify what they want,
and draft a short reply the developer could send back.
Reply in the same language the sender used. Be professional and concise.
Never invent commitments, prices, or deadlines on the developer's behalf.
```

Пользовательский — имя, email и текст обращения в размеченном виде.

Последняя строка системного промпта появилась после тестов: без неё модель
охотно обещала от лица владельца сроки и готовность взяться за проект.

Ответ ограничен JSON-схемой через structured output обоих провайдеров
(`response_json_schema` у Gemini, `json_schema` + `strict: true` у OpenAI).
Это убирает целый класс отказов «модель вернула почти-JSON»: формат гарантируется
на стороне API, а не выпрашивается в промпте.

### Fallback

Три уровня деградации:

| Ситуация | Поведение | `ai_status` |
|---|---|---|
| Основной провайдер ответил | Полный анализ | `ok` |
| Основной упал или завис | Переключение на резервный, причина в лог | `ok` |
| Все провайдеры недоступны | Нейтральные значения, пустой черновик | `fallback` |

**Третий уровень — обязательное требование ТЗ**: обращение всё равно сохраняется,
письма всё равно уходят, пользователь не видит ошибки. Первые два — сверху:
отказ одного провайдера гораздо вероятнее одновременного отказа обоих, и терять
из-за единичного 503 весь анализ незачем.

Таймаут на провайдера (`AI_TIMEOUT_SECONDS`) здесь не менее важен, чем сама цепочка.
Без него зависший основной провайдер заставил бы пользователя ждать сначала свой
полный таймаут, а потом ещё и резервный — и механизм отказоустойчивости оказался
бы хуже, чем его отсутствие.

Цепочка задаётся конфигом, а не кодом: `AI_PROVIDER_CHAIN=gemini,openai`.
Поменять порядок или убрать провайдера — правка одной строки без пересборки.

## 6. Что сделано с помощью AI

Проект написан в паре с Claude (Anthropic) в режиме диалога: обсуждение решений →
реализация → проверка. Ниже честная разбивка.

**Что генерировалось AI**

- Каркас проекта, разбивка по слоям, большая часть кода эндпоинтов, сервисов и репозиториев
- Тесты (35 штук) и HTML-шаблоны писем
- Docker-конфигурация, Caddyfile, настройка Alembic

**Какие промпты использовались**

Не «напиши форму обратной связи», а последовательное обсуждение: сравнение
FastAPI и Laravel под требования ТЗ, выбор SQLite против Postgres с разбором
аргументов против, выбор варианта деплоя, разбор необходимости Redis. Реализация
начиналась только после того, как решение было обосновано.

**Что пришлось исправлять**

Часть правок нашли тесты и проверки, а не первичная генерация:

1. **404 возвращал чужой формат ответа.** Обработчик был повешен на
   `fastapi.HTTPException`, а Starlette при несовпадении маршрута бросает свой
   базовый класс. Поиск обработчика идёт по MRO поднятого исключения, поэтому
   подкласс его не ловил — все 404 и 405 шли мимо общего конверта.

2. **Терялась таймзона у `created_at`.** SQLite не хранит смещение, и API отдавал
   время без маркера `Z`. Клиент прочитал бы UTC как локальное время и промахнулся
   на несколько часов. Исправлено типом-декоратором `UTCDateTime`.

3. **Миграции падали с `NameError`.** Alembic рендерит кастомный тип колонки
   полным именем, но импорт в файл миграции не добавляет. Починен шаблон
   `script.py.mako`, чтобы это не повторялось.

4. **Отладочные логи заливали файл.** При `DEBUG=true` aiosqlite и SQLAlchemy
   писали по строке на каждый SQL-запрос.

5. **`create_all` на старте конфликтовал с Alembic** — два источника схемы.
   Убран в пользу проверки, что миграции применены.

## 7. Хранение данных

Гибридная схема: каждый вид данных лежит там, где ему уместно.

| Данные | Где | Почему |
|---|---|---|
| Обращения + результат AI | SQLite | Доменные данные, нужны выборки и агрегаты |
| Логи запросов | `data/requests.log` | Прямое требование ТЗ |
| Логи приложения | `data/app.log` | Отладка, трассировка ошибок |
| Rate limiting | память + `data/rate_limit.json` | ТЗ предлагает файловый вариант |
| Статистика | вычисляется из БД | — |

### Почему SQLite, а не Postgres

ТЗ считает БД необязательным бонусом. SQLite даёт ровно те же демонстрируемые
навыки — схема, миграции, async ORM, индексы — но без отдельного сервиса,
конфликтов портов у проверяющего и лишнего контейнера в композе.

Нагрузка это подтверждает: форма обратной связи — это единицы записей в час,
на одном инстансе. Postgres здесь решал бы задачу, которой нет.

Типы колонок держатся переносимыми (`Uuid`, `UTCDateTime`), поэтому переезд на
Postgres — это смена `DATABASE_URL` и повторный прогон миграций, а не переписывание
запросов. Включён режим WAL: без него параллельное чтение во время записи
падало бы с `database is locked`.

### Почему статистика не в файле

ТЗ разрешает хранить её в файле, но отдельный файл-счётчик — это вторая копия
правды. Она расходится при каждой неудачной записи, каждом откате транзакции и
любой ручной правке строк, и сверять её нечем. Раз обращения уже в БД,
`/api/metrics` считается запросом `COUNT`/`GROUP BY` — на порядки меньше кода и
один источник правды.

### Rate limiting

Скользящее окно: по умолчанию 5 запросов с одного IP в час, настраивается.
Счётчики живут в памяти процесса под `asyncio.Lock` и сбрасываются в JSON-файл,
чтобы перезапуск нельзя было использовать для обнуления лимита.

Заблокированный запрос **не записывается** в окно. Иначе клиент, долбящийся в
эндпоинт, сам отодвигал бы себе время разблокировки и не вышел бы из бана никогда.

**Redis сознательно не используется.** Его ценность — общее состояние между
несколькими инстансами; здесь инстанс один, и распределённой задачи нет. Вызов по
сети на каждый запрос ради счётчика не окупается. При горизонтальном
масштабировании меняется одна реализация репозитория — бизнес-логика не затрагивается.

### Определение IP клиента

За обратным прокси реальный адрес клиента не в сокете, а в заголовке:
`CF-Connecting-IP` (Cloudflare) или `X-Forwarded-For` (Caddy). Если брать
`request.client.host`, все посетители попадут в один счётчик и лимит станет общим
на всех — ошибка тихая, локально не воспроизводится.

Обратная сторона: слепо доверять заголовку нельзя, иначе его подделают и обойдут
лимит. Доверие безопасно потому, что в продовой конфигурации приложение вообще
не публикует свой порт наружу (см. `docker-compose.prod.yml`) — попасть в него
можно только через прокси.

## Деплой

Продовая конфигурация — AWS EC2, Docker, Caddy для TLS, DNS через Cloudflare.

```bash
# на сервере
git clone <repo-url> && cd backend
cp .env.example .env && nano .env   # заполнить ключи
chmod 600 .env

docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d
```

Что делает продовый оверлей:

- поднимает Caddy, который сам получает и продлевает сертификат Let's Encrypt;
- **снимает публикацию порта приложения** — снаружи доступны только 80 и 443;
- переводит приложение в `ENVIRONMENT=production`, `DEBUG=false`.

Сертификаты хранятся в volume `caddy-data`. Без него Caddy перезапрашивал бы
сертификат при каждом рестарте и упёрся бы в лимит Let's Encrypt — 5 штук на
домен в неделю.

Security Group: наружу открыты только 80 и 443, SSH — с доверенного адреса.
Секреты в репозиторий не попадают: `.env` перечислен и в `.gitignore`, и в
`.dockerignore`, поэтому не оказывается ни в коммите, ни в слое образа.
